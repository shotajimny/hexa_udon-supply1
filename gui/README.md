# ヘキサうどん GUI

六角マップ、車両ごとの経路、途中待機、日開始時の実測燃料、合流地点・時刻、回答の採否を表示します。日付と日内stepを選択して計画を再生できます。

## 手元のMacで起動する

Python 3を用意し、このブランチを取得したリポジトリで実行します。ゲームサーバーとマップは手元のファイルを指定してください。

```bash
chmod u+x "/path/to/procon-server-darwin-arm64"
bash start_gui.sh \
  --server "/path/to/procon-server-darwin-arm64" \
  --maps "/path/to/sample_16.json" "/path/to/sample_24.json" "/path/to/sample_32.json"
```

`/path/to/` を実際のパスに置き換えます。Intel Macではdarwin-amd64、Linux x86_64ではlinux-amd64版を指定します。パスに空白がある場合も引用符を付けてください。

ブラウザーで `127.0.0.1:8765` を開きます。初回だけPython仮想環境とrequestsをインストールします。終了はターミナルで Ctrl+C。

「新しい試合」で選択マップを実行します。「受付を各日3秒に短縮」を外すと元の受付時間を使います。地形、車両数、燃料、dayStepsは変えません。指定したプロジェクトが参加し、残りのチームは待機します。実行は同時に1試合です。

サーバー実行ファイル・マップ・試合ログはこのブランチには同梱していません。`servers/` に対応サーバー、`maps/` にJSONを配置した場合は `bash start_gui.sh` だけで起動できます。

`--server`なしでも `bash start_gui.sh --runs /path/to/records` で保存済みの `*-config.json` と `*-result.json` を再生できます。`--port`でGUIポートを変更できます。

## 表示の意味

- マップ上の線と日内アニメーションは「送信した計画」です。リジェクトされた計画は点線で表示します。
- 車両の開始位置・開始燃料、翌日の状態は実サーバーのGET応答です。日内の燃料値を実測しているわけではありません。
- HTTP200だけでは採用としません。`revision > 0` が採用、`revision == -1` がリジェクトです。
- 車両を選ぶとその経路・合流イベントを強調します。待機中は車両の周りに輪を表示します。
- ホイールで拡大、ドラッグで移動、全体表示でリセットできます。
- 既存の記録には合流イベントが含まれていない場合があります。GUIから開始した試合ではPathSynchronizerの入出力も記録します。

記録は`--runs`のディレクトリに保存します。再実行前の記録は`archives/`に退避します。`main.py`のロジックはそのまま使い、別プロセス内の観測ラッパーでHTTP応答と同期経路を記録します。UIの更新は約1.2秒ごとです。

クラウド環境で動いているGUIはMacへ自動転送されません。Macで開くには、このブランチを取得して上記コマンドを実行してください。

## 獲得結果

募集要項9〜12ページに従って、試合全体の獲得種類数・日別獲得種類数の累積・試合全体の玉数・各日の種類数を表示します。系列brandの重複は除きます。

簡易サーバーに公式スコアAPIがないため、最後に採用された行動列を再生して集計します。巡回車だけが獲得し、同一車・同一スポットは1日1玉、在庫は日ごとに補充され、チーム内で共有します。補給車やリジェクトされた回答は獲得に数えません。途中で再提出された場合は最後の有効回答を使います。翌日の実測位置と再生の結果が合わない日は未集計にします。

日開始時にスポットにいる巡回車も、待機・移動にかかわらず獲得に数えます。在庫数と「同じ巡回車・同じスポットは1日1玉」の制限を適用し、補給車は獲得しません。これは公式スコアの実測値ではありません。

実測の獲得履歴がある場合は「獲得履歴を読み込む」から、自チーム分のJSON配列を読み込めます。この履歴を優先して表示します。履歴は、同じ獲得を重複して入れないでください。

```json
[
  {"day": 0, "brand": 0, "count": 1},
  {"day": 0, "brand": 1, "count": 2},
  {"day": 1, "brand": 0, "count": 1}
]
```

dayは0始まり、countは玉数です。試合開始前や未確定の日は未取得・未集計と表示し、獲得数0と区別します。集計途中の試合全体の値は集計済みの日だけの合計です。

未取得ブランドは、マップに存在するbrand IDの一覧と獲得済みブランドの差分として、各日と試合全体に表示します。全種類取得済みなら「なし」、未集計の日は「未集計」です。試合全体の一覧は全日分の集計が揃うと表示します。

巡回車の経路は試合全体の未取得ブランドを最優先に選択します。未取得ブランドは近傍候補数の制限を受けず全てA*で評価し、燃料で到達できる車を優先します。当日に獲得済みのブランドは別スポットでも候補から除外します。同期後の経路を当日の取得予定に反映し、採用回答と翌日の実位置の照合によって試合全体の履歴を更新します。最終集計が揃い未取得ブランドがなくなると「全種類制覇」と表示します。到達不能なブランドや時間・燃料不足があるマップでは未達になる場合があります。

## 複数プロジェクトで同じ試合に参加する

起動後、GUIの「参加プロジェクト」に、各プロジェクトの`main.py`があるフォルダを1行ずつ指定してください。上からチーム0、チーム1…として「新しい試合」で同じサーバーへ同時参加します。`~`からのパスも使えます。マップのチーム数以内で指定します。

例えば、Macでホームフォルダ直下に2つのプロジェクトがある場合：

```text
~/hexa_udon-client
~/hexa_udon-single-supply
```

実際の保存場所が異なる場合はそのフォルダを指定してください。起動時に`--projects`で指定することもできます。

```bash
bash start_gui.sh \
  --server "/実際のパス/procon-server-darwin-arm64" \
  --maps "/実際のパス/sample_24.json" \
  --projects "$HOME/hexa_udon-client" "$HOME/hexa_udon-single-supply"
```

「表示チーム」または比較表の行を選ぶと、そのチームの経路、車両、回答の採否、日別結果、未取得ブランドを表示します。比較表には全参加チームの獲得種類数・日別種類数の累積・獲得数・未取得ブランドを表示します。獲得履歴の読み込みは選択中のチームに適用します。記録はチーム別に保存し、再起動後も切り替えて再生できます。

各プロジェクトは既存の`requests`による`http://127.0.0.1:8080`への通信を使うPython版`main.py`を対象とします。GUIがチームごとの接続先とトークンを振り分けるので、元のAPIコードを変更する必要はありません。各プロジェクトに`venv/bin/python`があればそれを使い、なければGUIと同じPythonを使います。必要な依存パッケージは各環境にインストールしてください。

## 回答速度

チーム比較表に平均・合計回答時間を表示し、選択中のチームには日別の計算時間・通信時間・回答時間を表示します。単位はmsです。

- 計算時間：その日のデータを初めて受信してから、回答の送信を開始するまで。
- 通信時間：回答送信を開始してから、サーバー応答を受け取るまで。
- 回答時間：計算時間と通信時間の合計。

各日の最後に採用された回答を集計し、リジェクトされた回答は平均・合計から除外します。同じ日のデータを再取得しても計測開始時刻はリセットしません。途中集計は計測済みの日だけを使います。旧記録には計測値がないため「未計測」と表示します。新しい試合から計測されます。計測は単調増加時計を使い、GUIによる観測処理やクライアント内の待機も含みます。この表示はローカル計測値であり、公式サーバーの採点用経過時間とは異なります。

補給方式の比較表には「日開始時の移動不能車日数」「補給計画回数」「同じ車への連続補給・最大」も表示します。移動不能車日数は、日開始時の実測燃料が出発セルの移動燃料を下回る巡回車の延べ日数です（燃料不足待機の総step数ではありません）。補給回数・連続回数は同期後に成立する計画の記録から集計し、公式サーバーの実測補給回数ではありません。
